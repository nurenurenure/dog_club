# Клуб собаководства

Учебный Go-бэкенд информационной системы клуба собаководства: учёт членов клуба
и собак, ветеринарные записи, племенная работа, мероприятия, документы и отчётность.
Монорепозиторий: Go-бэкенд в `backend/`, веб-клиент на React — в `frontend/`.
REST API работает и без клиента.

## Возможности

- Приглашения и подтверждение email, вход и восстановление пароля, JWT access/refresh.
- Один аккаунт человека и несколько назначенных администратором профилей;
  в каждой сессии активен один профиль, права не объединяются.
- Карточки членов клуба, контакты, адреса и статусы членства.
- Собаки, идентификаторы, владельцы, родословные, внешние сведения о родителях и титулы.
- Осмотры, диагнозы, вакцинации, расчёт сроков и медицинские допуски.
- Заявки на вязку, проверка пары с запретом близкого родства, подбор пары, решения
  эксперта, вязки, помёты и регистрация щенков.
- Мероприятия шести типов, участники, классы, расписание, явка и экспертные результаты.
- Журнал проведённой дрессировки и допуски инструкторов по видам занятий.
- Закрытый реестр документов, загрузка PDF/JPEG/PNG, девять PDF-форм,
  сводный отчёт в JSON/PDF/CSV.
- Автоматические письма и напоминания через локальный Mailpit, очередь с повторами.
- Проверки состояния, административные метрики, резервирование и восстановление.

Изменения предметных данных проверяют версии и атомарно сохраняют историю.
Правила триггеров лаб. 3 реализованы в сервисах Go, а не в PL/pgSQL: неактивные
собаки, пересечение вакцинаций, родословная на три поколения, близкое родство,
подбор пары, допуск на мероприятие и даты документов.
Владельцы читают разрешённые сведения о своих текущих собаках только при активном
членстве. Администратор управляет аккаунтами и профилями; профессиональные права
сотрудника, ветеринара или эксперта ему автоматически не предоставляются.

## Стек и архитектура

Go 1.26, Chi v5, pgx/v5/pgxpool, PostgreSQL 18, Goose, OpenAPI 3.1.1,
`log/slog`, Docker Compose. Версии Go-зависимостей закреплены в `backend/go.mod` и `backend/go.sum`.
Модуль `dogclub.local/backend` использует локальное имя.

Модульный монолит, один API-процесс и одна БД:

```text
HTTP → Handler → Service → Repository → PostgreSQL
```

Межмодульные вызовы идут через публичные сервисы в общей транзакции.
Документы хранятся в приватном каталоге, метаданные и контрольные суммы — в БД.
Фоновый обработчик доставляет письма из PostgreSQL outbox; SMTP и файловый I/O
выполняются вне предметных транзакций. Микросервисы, ORM, Redis и отдельный брокер
не используются.

```text
backend/
  cmd/         API, миграции, bootstrap администратора, healthcheck, проверка файлов
  internal/    предметные модули, композиция приложения и инфраструктура
  migrations/  встроенные SQL-миграции и их проверки
  api/         OpenAPI и проверки контракта
  docs/        архитектурные решения, правила модулей, эксплуатация
frontend/      веб-клиент (React, TypeScript, CSS Modules)
scripts/       резервирование, восстановление, импорт файлов, сквозная проверка
compose.yaml   общий запуск в Docker
```

## Быстрый запуск в Docker

Нужны Docker Engine/Desktop и Docker Compose с поддержкой `up --wait`.
Для первой сборки требуется доступ к реестру Docker и Go module proxy.
Go на компьютере для контейнерного запуска не требуется.
Все команды выполняются из корня репозитория.

```sh
cp -n .env.example .env
openssl rand -hex 16
openssl rand -base64 32
```

В `.env` замените `POSTGRES_PASSWORD` и пароль в `DATABASE_URL` одной случайной
шестнадцатеричной строкой, а `AUTH_JWT_KEY` — отдельным base64-ключом минимум
из 32 случайных байт. Существующую `.env` не заменяйте примером. Секреты и
пользовательские файлы исключены из Git и контекста Docker-сборки.

```sh
docker compose config --quiet
docker compose up --build -d --wait web
curl -fsS http://127.0.0.1:8081/health/ready
```

Compose ждёт готовности PostgreSQL, выполняет одноразовый сервис миграций и
проверку файлов, затем запускает API и веб-клиент. Сам API миграций не выполняет.
Только API без клиента — `docker compose up --build -d --wait api`.

| Сервис | Локальный адрес |
| --- | --- |
| Веб-клиент | `http://127.0.0.1:8081` |
| REST API | `http://127.0.0.1:8080/api/v1` |
| Mailpit | `http://127.0.0.1:8025` |
| SMTP Mailpit | `127.0.0.1:1025` |
| PostgreSQL | `127.0.0.1:5432` |

Первый администратор создаётся приглашением:

```sh
docker compose run --rm --no-deps --entrypoint /admin api bootstrap admin admin@dogclub.test
```

Возьмите код из письма в Mailpit и активируйте аккаунт на вкладке «Приглашение»
веб-клиента, затем войдите. Без клиента — `POST /api/v1/auth/activate` и
`POST /api/v1/auth/login`, примеры в [авторизации](backend/docs/auth.md).
Готовых аккаунтов и паролей в миграциях нет. Новых пользователей приглашает
администратор через защищённое API; открытой регистрации нет.

Остановка с сохранением данных: `docker compose down`. Команда `down --volumes`
удаляет постоянные тома и не подходит для обычной остановки.
Перед переходом с API на хосте остановите старый процесс. Если в БД уже есть
зарегистрированные файлы, перенесите их проверяемым импортом.
Подробности запуска, файловых томов, резервирования и восстановления —
в [инструкции эксплуатации](backend/docs/operations.md).

## Запуск Go на хосте

Нужен Go 1.26.x и подготовленная `.env` с loopback-адресами и
`LOCAL_COMPOSE=false`. Не запускайте второй API одновременно с контейнерным.
Go-команды выполняются из `backend/`, `.env` остаётся в корне.

```sh
cd backend
set -a
. ../.env
set +a

go mod download
docker compose up -d --wait db mailpit
go run ./cmd/migrate up
go run ./cmd/api
```

Приложение читает окружение процесса, а не файл `.env` самостоятельно.
При изменении порта PostgreSQL обновите также `DATABASE_URL`.
`go mod download` скачивает закреплённые зависимости; `go mod tidy` нужен
при изменении зависимостей, а не для каждого запуска.

## API и состояние сервиса

[OpenAPI](backend/api/openapi.yaml) описывает 151 операцию. Успешные ответы — JSON DTO,
ошибки — RFC 9457 (`application/problem+json`) со стабильным `code`, `request_id`
и ошибками полей. Неизвестные поля JSON отклоняются. Ответы имеют
`Cache-Control: no-store` и `X-Request-ID`.
Общий формат и примеры — в [HTTP-контракте](backend/docs/http-api.md).

| Маршрут | Поведение |
| --- | --- |
| `GET /health/live` | 200, живой процесс, без проверки БД |
| `GET /health/ready` | 200 при доступной БД; 503 при сбое или shutdown |
| `GET /api/v1/operations/metrics` | Агрегаты HTTP, pgxpool и почтовой очереди; только admin |

При недоступной БД процесс остаётся живым; readiness восстанавливается без
перезапуска API. SIGTERM прекращает приём запросов, дожидается активных HTTP-запросов,
останавливает worker и закрывает пул. Логи содержат шаблоны маршрутов, статусы,
request ID и длительность, без тел запросов, query strings, DSN и токенов.

## Конфигурация

Ниже значения Go-конфигурации и публикуемых Compose-портов.
Compose явно задаёт внутренние адреса `db:5432`, `mailpit:1025`,
`0.0.0.0:8080`, каталог `/data/documents`, `LOCAL_COMPOSE=true` и локальную
HTTP-cookie без Secure. Порты компьютера публикуются только на `127.0.0.1`.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DATABASE_URL` | обязательна | Строка подключения pgx; ошибки разбора обезличены |
| `HTTP_ADDR` | `127.0.0.1:8080` | Адрес HTTP-сервера |
| `LOG_LEVEL` | `info` | Уровень slog: debug, info, warn, error |
| `HTTP_READ_HEADER_TIMEOUT` | `5s` | Чтение заголовков |
| `HTTP_READ_TIMEOUT` | `15s` | Чтение запроса |
| `HTTP_WRITE_TIMEOUT` | `15s` | Запись ответа |
| `HTTP_IDLE_TIMEOUT` | `60s` | Ожидание следующего запроса |
| `DB_PING_TIMEOUT` | `1s` | Readiness Ping и установление соединения с БД |
| `SHUTDOWN_TIMEOUT` | `10s` | Ожидание завершения HTTP-запросов |
| `AUTH_JWT_KEY` | обязательна | Base64 от минимум 32 случайных байт; отдельный секрет |
| `AUTH_JWT_ISSUER` | `dogclub.local` | Проверяемый издатель access JWT |
| `AUTH_JWT_AUDIENCE` | `dogclub-api` | Проверяемая аудитория access JWT |
| `AUTH_IO_TIMEOUT` | `10s` | Таймаут операций auth с БД/почтой |
| `AUTH_COOKIE_SECURE` | `true` | Secure refresh-cookie; в локальном `.env.example` — false |
| `SMTP_ADDR` | `127.0.0.1:1025` | Локальный SMTP; в Compose — `mailpit:1025` |
| `MAIL_FROM` | `noreply@dogclub.test` | Адрес отправителя локальных писем |
| `MAILPIT_SMTP_PORT` | `1025` | Публикуемый SMTP-порт Compose |
| `DOCUMENTS_DIR` | `var/documents` | Закрытые файлы; 0700, резервирование вместе с БД |
| `MAILPIT_HTTP_PORT` | `8025` | Порт интерфейса Mailpit |
| `LOCAL_COMPOSE` | `false` | Явное разрешение локального контейнерного режима; Compose задаёт true |
| `NOTIFICATIONS_ENABLED` | `true` | Включение фонового worker, без отключения outbox |
| `API_PORT` | `8080` | Публикуемый порт API в Compose |
| `POSTGRES_USER` / `POSTGRES_DB` | `dogclub` / `dogclub` | Роль и база PostgreSQL в Compose |
| `POSTGRES_PASSWORD` | обязательна | Пароль PostgreSQL; для Compose используйте URI-safe строку |
| `POSTGRES_PORT` | `5432` | Публикуемый порт PostgreSQL |

Таймауты задаются положительными Go duration. Пул: максимум 4 соединения,
минимум 0. Без `LOCAL_COMPOSE` отключение Secure разрешено только на loopback;
в Compose исключение предназначено исключительно для локальной сети проекта.
Origin-проверка остаётся включена. Внешняя SMTP-доставка не настроена.

Каталог документов имеет права 0700, файлы 0600. Резервная копия должна
согласованно включать PostgreSQL и файлы. Команды и ограничения —
в [эксплуатации](backend/docs/operations.md).

## Миграции и начальные данные

В `backend/migrations/` находятся 14 встроенных миграций: исходная схема и справочники,
авторизация, карточки членов и собак, ветеринария, племенная работа, мероприятия,
документы, очередь уведомлений, дрессировка и активность статусов собак. Итоговая схема содержит 65 прикладных
таблиц и историю Goose. Справочники заполнены; препаратов вакцин, пользователей,
членов клуба и собак начальные миграции не создают. Препараты с подтверждёнными
сроками добавляет ветеринар через API.

```sh
docker compose run --rm --no-deps --entrypoint /migrate api status
docker compose run --rm --no-deps --entrypoint /migrate api up
```

`up` пропускает применённые версии. Исходная миграция рассчитана на новую БД;
она откажется работать с занятой схемой без истории Goose. `down` откатывает
одну версию и может быть запрещён при наличии новых предметных данных.
Проверяйте откаты только на одноразовых базах. Происхождение схемы, исправления
исходного SQL и ограничения переноса — в [аудите](backend/docs/database-audit.md).

## Проверки

В Docker, без Go на компьютере:

```sh
docker compose run --build --rm checks
```

Команда выполняет проверку модулей, `go vet`, сборку и все PostgreSQL-тесты с
`-race`. Интеграционные тесты создают и удаляют собственные случайные БД;
роль должна иметь право CREATEDB.

Веб-клиент — typecheck и тесты Vitest, тоже без Node на компьютере:

```sh
docker compose run --build --rm web-checks
```

Разработка клиента и его проверки на хосте — в [frontend/README.md](frontend/README.md).

На хосте, из `backend/`:

```sh
gofmt -l cmd internal migrations api
go vet ./...
go test -race ./...
go build ./...
go mod verify
```

Для PostgreSQL-тестов после экспорта `../.env`:

```sh
export DOGCLUB_TEST_DATABASE_URL="$DATABASE_URL"
go test -race -tags=integration ./...
```

Для полной проверки работающего контейнера нужны Python 3 stdlib и Docker
(из корня репозитория):

```sh
python3 scripts/verify.py
```

Сценарий изолирован от рабочей `.env` и данных. Он проверяет права, почту,
сбои и перезапуск, восстановление непустой БД с PDF, а также 50 параллельных
клиентов. Подготовка сессий соблюдает ограничение входа и занимает несколько минут.
Фактические результаты и границы измерений — в [отчёте](backend/docs/verification.md).

## Границы реализации

Репозиторий содержит серверную часть для локального запуска. Публичный хостинг/TLS,
внешний SMTP, REST-ящик уведомлений/WebSocket, внешние интеграции и расширенный
мониторинг не настроены. Веб-клиент строится по шагам: готовы вход, приглашение,
восстановление пароля, оболочка с меню по ролям и аккаунт; экраны разделов
добавляются следующими шагами.
