# Клуб собаководства — backend

Этапы 01–09 и части 1–4 этапа 10: инфраструктура, миграции, REST-контракты, авторизация, члены клуба,
собаки, ветеринарный и племенной учёт, мероприятия, документы и файлы.
Go 1.26, Chi v5, pgx/v5/pgxpool, PostgreSQL 18, REST JSON. API работает на хосте,
в Compose запускаются PostgreSQL и локальная почта Mailpit. Одна учётная запись
может иметь несколько назначенных администратором профилей; активен один профиль
на сессию. Добавлены карточки членов клуба, контакты, адреса, собаки, владельцы,
родословные, записи титулов, осмотры, вакцинации, медицинский допуск, мероприятия,
участники, расписание, результаты, реестр документов, копии и девять PDF-форм,
сводный отчёт в JSON/PDF/CSV без серверного архива.
React и остальные предметные модули появятся на следующих этапах.

## Локальный запуск

Все команды выполняются в этой папке:

```bash
cd /Users/muraveva/DOGCLUB/backend
cp -n .env.example .env
```

Если используется новый пример, в `.env` замените `replace_with_random_hex_password`
на одинаковый пароль в `POSTGRES_PASSWORD` и `DATABASE_URL`. Удобно использовать
случайную шестнадцатеричную строку, например результат `openssl rand -hex 16`.
Пример не содержит настоящих секретов; `.env` исключён из Git.
Для `AUTH_JWT_KEY` сгенерируйте отдельный ключ командой `openssl rand -base64 32`
и замените соответствующий placeholder в `.env`. Сохраняйте ключ между запусками;
его замена делает ранее выданные access JWT недействительными.

Переменные `DATABASE_URL` и настройки PostgreSQL должны соответствовать друг
другу. Если изменяете порт, поменяйте `POSTGRES_PORT` и порт в `DATABASE_URL`.
При использовании произвольных символов в пароле необходим URL encoding
в строке подключения. Приложение `.env` автоматически не читает.

Экспортируйте подготовленный локальный файл и запустите БД и приложение:

```bash
set -a
. ./.env
set +a

go mod download
docker compose config --quiet
docker compose up -d --wait db mailpit
go run ./cmd/migrate status
go run ./cmd/migrate up
go run ./cmd/api
```

`go mod download` скачивает закреплённые зависимости. `go mod tidy` нужен при
изменении зависимостей, а не для каждого запуска. Файл `go.sum` хранится в Git
вместе с `go.mod`. Повторный `migrate up` безопасно пропускает применённые версии.
После первого развёртывания для запуска API достаточно `go run ./cmd/api`.
Mailpit принимает письма на `127.0.0.1:1025`; интерфейс доступен по
[http://127.0.0.1:8025](http://127.0.0.1:8025). Письма наружу не отправляются.

После миграций создайте приглашение первому администратору, указав выбранные
логин и email (из терминала с экспортированным `.env`):

```bash
go run ./cmd/admin bootstrap admin admin@dogclub.test
```

Откройте письмо в Mailpit и активируйте приглашение через API со своим паролем.
Пример запроса приведён в [docs/auth.md](docs/auth.md). Готовых аккаунтов и паролей
нет. После активации администратора CLI больше не создаёт администраторов:
новые пользователи и профили назначаются через защищённое API.

Второй терминал, из той же папки:

```bash
curl -i http://127.0.0.1:8080/health/live
curl -i http://127.0.0.1:8080/health/ready
```

| Маршрут | Результат |
| --- | --- |
| `GET /health/live` | `200 {"status":"ok"}`, без обращения к БД |
| `GET /health/ready` | `200 {"status":"ready"}` при успешном Ping |
| `GET /health/ready` при сбое БД или shutdown | `503 {"status":"not_ready"}` |

Ответы имеют `Content-Type: application/json`, `Cache-Control: no-store` и
`X-Request-ID`. Ошибки БД не передаются в ответ. Auth-маршруты находятся под
`/api/v1`; описание модулей — в [docs/auth.md](docs/auth.md),
[docs/members.md](docs/members.md), [docs/dogs.md](docs/dogs.md),
[docs/veterinary.md](docs/veterinary.md), [docs/breeding.md](docs/breeding.md),
[docs/events.md](docs/events.md), [docs/documents.md](docs/documents.md) и OpenAPI.

## Общий HTTP-контракт

Спецификация [api/openapi.yaml](api/openapi.yaml) в формате OpenAPI 3.1.1
описывает 139 операций существующих маршрутов и общие схемы ошибок. Swagger UI
пока не добавлен. Последующие модули также используют `/api/v1`.

Ошибки приложения возвращаются по RFC 9457 с
`Content-Type: application/problem+json` и `Cache-Control: no-store`:

```json
{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "code": "not_found",
  "detail": "Ресурс не найден.",
  "request_id": "example-request-id"
}
```

`type=about:blank` обозначает обычный HTTP-статус, `title` — его стандартное
английское имя из Go, `code` — стабильное машинное уточнение. Клиент использует
статус и код, не разбирая текст `detail`. Сообщения пользователю — по-русски.
`request_id` совпадает с `X-Request-ID` и идентификатором в логах. Для 405
заголовок `Allow` перечисляет разрешённые методы. Ответ health/readiness 503
сохраняет собственный DTO `{"status":"not_ready"}`.

`internal/platform/httpapi` предоставляет:

- `DecodeJSON` и `DecodeJSONLimit`: один JSON-объект UTF-8, проверка
  `Content-Type: application/json` (разрешён `charset=utf-8`), отклонение
  неизвестных полей, пустого тела, `null`, неверных типов и лишних данных.
  Ограничение по умолчанию — 1 МиБ всего тела, включая пробелы; отдельный
  обработчик может задать положительный предел в байтах.
- `ValidationProblem`: ошибки значений полей с HTTP 422 и массивом `errors`
  (`field`, `code`, `message`). `field` использует JSON-имя, вложенные поля —
  запись через точку. При отсутствии ошибок возвращается `nil`.
- `WriteJSON`: успешный ответ DTO без общей оболочки. Кодирование происходит
  до отправки заголовков; ошибка кодирования обрабатывается recovery как 500.
- `WriteProblem` и `NewProblem`: безопасные ошибки с HTTP-статусом и кодом.

| Статус | Код | Причина |
| --- | --- | --- |
| 400 | `invalid_json` | Некорректная структура JSON, неизвестные поля или неверные типы |
| 413 | `body_too_large` | Превышен предел тела |
| 415 | `unsupported_media_type` | Неверный/отсутствующий Content-Type либо неподдерживаемая кодировка |
| 422 | `validation_failed` | Не пройдена проверка значений полей |
| 404 | `not_found` | Не найден ресурс или маршрут |
| 405 | `method_not_allowed` | Метод не поддерживается для маршрута |
| 500 | `internal_error` | Внутренняя ошибка без раскрытия подробностей |

Handler сначала разбирает JSON, затем проверяет формат полей и вызывает
Service. При ошибке разбора частично заполненный DTO отбрасывается. Handler
преобразует известные ошибки Service в HTTP-ответ; предметные правила остаются
в Service, SQL — в Repository. Эти два слоя не зависят от `httpapi`. Нельзя
передавать исходный `error.Error()`, персональные данные или значения клиента
в `detail` и сообщения полей. Универсального преобразования SQLSTATE в HTTP нет.

Для проверки 404 и 405 при запущенном API:

```bash
curl -i http://127.0.0.1:8080/api/v1/absent
curl -i -X POST http://127.0.0.1:8080/health/live
```

Ожидаются соответственно 404 с `code=not_found` и 405 с
`code=method_not_allowed`, `Allow: GET`. Общие механизмы POST/валидации также
проверяются тестовыми маршрутами, которые не входят в работающий API.

## Проверка недоступности и восстановления БД

При работающем API выполните во втором терминале:

```bash
docker compose stop db
curl -i http://127.0.0.1:8080/health/live
curl -i http://127.0.0.1:8080/health/ready

docker compose start db
```

Пока БД остановлена, ожидаются соответственно 200 и 503. После восстановления
PostgreSQL повторный readiness возвращает 200 без перезапуска API. Сервис также
можно запустить до старта БД: корректная строка подключения с недоступным сервером
не препятствует запуску HTTP. Ошибки конфигурации останавливают процесс.

Ctrl+C в терминале API или SIGTERM процессу запускает graceful shutdown:
readiness снимается, сервер прекращает принимать соединения, текущие запросы
завершаются в пределах `SHUTDOWN_TIMEOUT`, затем закрывается пул. Если срок
истёк, контексты запросов отменяются, соединения закрываются принудительно,
процесс завершается с ошибкой.

`go run` использует промежуточный Go-процесс. Для проверки SIGTERM направляйте
сигнал самому бинарному файлу; его можно запустить так:

```bash
mkdir -p bin
go build -o bin/api ./cmd/api
./bin/api
```

Остановка инфраструктуры после проверки:

```bash
docker compose down
```

Эта команда сохраняет именованный volume. Не используйте `down -v`, если нужны
данные. Для PostgreSQL 18 volume смонтирован в `/var/lib/postgresql`, согласно
[документации официального образа](https://hub.docker.com/_/postgres).
Переменные `POSTGRES_*` инициализируют только пустой volume; изменение пароля
в `.env` не меняет пароль уже созданной БД.

Порты PostgreSQL и HTTP по умолчанию доступны только на loopback. Эта конфигурация
предназначена для локальной разработки; `sslmode=disable` относится к ней.
Compose использует образ `postgres:18` и может получать обновления в пределах
этой основной версии. Исходный SQL и init-скрипты к контейнеру не подключаются:
прикладные таблицы и справочники создаются только явной командой миграций.

## Миграции и справочники

После экспорта `.env`:

```bash
go run ./cmd/migrate status
go run ./cmd/migrate up
```

`status` показывает версии и состояние `pending`/`applied`. На новой БД он
не создаёт таблиц. `up` применяет одиннадцать миграций: исходную схему, начальное
наполнение, авторизацию, изменения members, dogs, veterinary, breeding, events и documents.
Первые две версии создают
33 таблицы snake_case, 37 FK, PK связующих таблиц и уникальность идентификатора
собаки; затем 68 значений в 17 справочниках. Препаратов вакцин пока нет по
согласованию пользователя. Личные данные и карточки собак не создаются.
Третья версия добавляет семь auth-таблиц и стабильные коды шести ролей.
Четвёртая удаляет старый club_member.role_id и его FK, добавляет версию карточки,
историю member_changes и увеличивает длину контакта до 254 символов.
Пятая вводит обязательность непустого идентификатора собаки, рост/вес и версию,
необязательные FK родителей и внешние сведения, одну родословную на собаку,
реквизиты титулов и dog_changes. Шестая добавляет единицы двух периодов препарата,
наследственность диагноза, авторов/версии/снимки/отмену медицинских записей,
заключения и их основания, veterinary_changes. Седьмая добавляет заявки и решения
по вязкам, помёты, связи щенков и breeding_changes. Восьмая добавляет площадки,
классы/расписание/участников/экспертов мероприятий, результаты и event_changes.
Девятая добавляет реестр/историю файлов и документов, явные предмет/получателя,
категории, статусы и два типа печатных карточек. Десятая добавляет подтверждённую
дату регистрации собаки, ссылки на решения/помёты и три новые формы.
Одиннадцатая добавляет связи документов с мероприятиями и результатами,
список участников, протокол и диплом.
Итого 58 прикладных таблиц, история Goose и 110 FK. Начальных пользователей,
профилей и карточек нет.
Справочник role и существующие карточки сохраняются;
старые значения role_id не преобразуются в полномочия.

Начальная схема предназначена для новой БД. Если public уже содержит таблицы,
представления или последовательности без истории Goose, команда откажется
начинать миграции. Перенос существующей учебной схемы требует отдельного плана.
Миграции встроены в бинарный файл и используют advisory lock PostgreSQL;
HTTP-сервер самостоятельно их не запускает. Для работы из другой папки можно
собрать отдельный бинарный файл: `go build -o bin/migrate ./cmd/migrate`.

`go run ./cmd/migrate down` откатывает ровно одну версию. Откат seed при наличии
ссылок отклоняется; откат схемы удаляет её данные. Проверять полный откат следует
только на одноразовой БД. Для обычной остановки и запуска используйте Compose,
а не откат миграций.
Откат четвёртой версии разрешён только при пустом каталоге членов: удалённые
значения старой роли невозможно восстановить по профилям без выдумывания данных.
При существующих карточках Down откажется атомарно, сохранив схему и данные.
Откат пятой версии аналогично требует пустого каталога собак: старая модель
не позволяет сохранить новые сведения о родословных, измерениях и истории.
Up не исправляет старые неверные идентификаторы и родителей выдуманными данными:
такие записи нужно предварительно проверить и исправить отдельно.
Откат шестой версии требует пустых клинических записей/истории и отсутствия
настроенных препаратов. Старые даты и неизвестные медицинские сведения при Up
сохраняются; единицы периодов, авторы и наследственность не подставляются.
Откат седьмой версии отказывается при наличии новых племенных данных. Up сохраняет
старые вязки и их счётчики; неоднозначные breeding_id требуют отдельного исправления.
Восьмая версия сохраняет старые даты мероприятий без назначения часового пояса
и текст судьи; неоднозначные achievement_id требуют аудита. Down отказывается
при наличии новых сведений мероприятий.

Команда принимает `DATABASE_URL` из окружения, работает с public и завершается
по сигналу или таймауту 2 минуты. Подключение имеет таймаут 5 секунд. Пароли,
DSN и детали значений PostgreSQL в ошибки не включаются; SQLSTATE сохраняется.

Девятая миграция сохраняет неоднозначную старую связь документа с человеком,
не назначая получателя/автора; старые записи получают статус legacy. Down
отказывается при новых сведениях документов и файлов.

## Конфигурация

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DATABASE_URL` | обязательна | Строка подключения pgx; ошибки разбора обезличены |
| `HTTP_ADDR` | `127.0.0.1:8080` | Адрес HTTP-сервера |
| `LOG_LEVEL` | `info` | Уровень slog: debug, info, warn, error |
| `HTTP_READ_HEADER_TIMEOUT` | `5s` | Чтение заголовков |
| `HTTP_READ_TIMEOUT` | `15s` | Чтение запроса |
| `HTTP_WRITE_TIMEOUT` | `15s` | Запись ответа |
| `HTTP_IDLE_TIMEOUT` | `60s` | Ожидание следующего запроса |
| `DB_PING_TIMEOUT` | `1s` | Readiness Ping и установление соединения с БД |
| `SHUTDOWN_TIMEOUT` | `10s` | Ожидание завершения HTTP-запросов |
| `AUTH_JWT_KEY` | обязательна | Base64 от минимум 32 случайных байт; отдельный секрет |
| `AUTH_JWT_ISSUER` | `dogclub.local` | Проверяемый издатель access JWT |
| `AUTH_JWT_AUDIENCE` | `dogclub-api` | Проверяемая аудитория access JWT |
| `AUTH_IO_TIMEOUT` | `10s` | Таймаут операций auth с БД/почтой |
| `AUTH_COOKIE_SECURE` | `true` | Secure refresh-cookie; в локальном `.env.example` — false |
| `SMTP_ADDR` | `127.0.0.1:1025` | Только loopback IP, локальный Mailpit |
| `MAIL_FROM` | `noreply@dogclub.test` | Адрес отправителя локальных писем |
| `MAILPIT_SMTP_PORT` | `1025` | Публикуемый SMTP-порт Compose |
| `DOCUMENTS_DIR` | `var/documents` | Закрытые файлы; 0700, резервирование вместе с БД |
| `MAILPIT_HTTP_PORT` | `8025` | Порт интерфейса Mailpit |

Для `DOCUMENTS_DIR` сервер создаёт закрытый каталог; при существующих открытых
правах откажется запускаться. В эксплуатации используйте постоянный абсолютный
путь. Резервируйте папку и PostgreSQL согласованно; подробности — docs/documents.md.

`AUTH_COOKIE_SECURE=false` разрешён только при loopback IP в `HTTP_ADDR`.
При смене `MAILPIT_SMTP_PORT` согласованно измените порт `SMTP_ADDR`.

Таймауты должны быть положительными Go duration. Пул содержит максимум
4 соединения, минимальное количество — 0. Технические HTTP-события пишутся
через slog в JSON. Журналируются шаблон маршрута, метод, статус, request ID,
объём ответа и длительность; тела, query string, DSN, токены и значения panic
не записываются.

## Проверки

```bash
gofmt -l cmd internal migrations api
go vet ./...
go test -race -count=1 ./...
go build ./...
go mod verify
docker compose config --quiet
```

следуют Handler → Service → Repository. Предметные модули работают через публичный
auth.Service.WithAccess для проверки прав и транзакции с PostgreSQL. Dogs проверяет
членство и владельцев через публичный members.Service в той же транзакции;
приватные репозитории других модулей закрыты. Veterinary проверяет пациента
через dogs и членство/ссылки через members в той же транзакции. Проверка
даты рождения передаётся dogs через публичную политику veterinary без циклического импорта.
Breeding вызывает публичные dogs/veterinary в той же транзакции; публичная
DogPolicy защищает зарегистрированные племенные факты при изменении карточек.
Письма отправляются через интерфейс Mailer и локальный SMTP-адаптер в
`internal/platform/mail`. `cmd/admin` использует тот же сервис для первого приглашения.
Бизнес-модули позднее будут следовать Handler → Service → Repository,
межмодульные вызовы — через публичные сервисы.

Миграции: `cmd/migrate` → Goose → pgx/stdlib → PostgreSQL. Начальные SQL
встроены в пакет `migrations`; зависимости миграций не подключены к API.
`internal/platform/httpapi` содержит общие JSON/DTO-механизмы и ошибки;
`api/openapi.yaml` описывает HTTP-контракт. Бизнес-сервисы и репозитории не
зависят от HTTP-пакета. OpenAPI-валидатор подключён только к тестам.
Исходный пакет находится в `../dogclub_agent_context_plan_mode (2)/` и остаётся
без изменений. Его `02_sql_extracted_REFERENCE_ONLY.sql` не является миграцией.
Ошибки исходного SQL воспроизведены в одноразовой PostgreSQL: повторные имена
индексов и повторный `has` внутри `Club_member` и `Document`. Согласованные
исправления и недостающие ключи реализованы в новых миграциях; подробности
и отложенные изменения перечислены в аудите.
Новые сущности и изменения схемы требуют отдельного согласования.

Этапы 04–10 (части 1–4 этапа 10) включают аккаунты, профили, приглашения, сессии, локальную почту,
учёт членов клуба, собак, ветеринарии, племенной работы, мероприятий, документов и сводный отчёт.
React, дополнительная аналитика/формы, оповещения и внешняя SMTP-доставка отложены. Новые owner-операции также должны проверять членство;
профиль администратора не даёт профессиональных полномочий других профилей.
