# Автоматические письма и напоминания

Сервер отправляет письма автоматически через существующий локальный SMTP.
Mailpit принимает их для разработки: просмотр http://127.0.0.1:8025.
Это не доставка на внешние адреса Gmail/Яндекс. Внешний SMTP, REST-ящик
уведомлений, WebSocket и пользовательские подписки не реализованы.

## События и получатели

| Событие | Когда отправляется |
| --- | --- |
| Регистрация собаки | Подтверждена дата регистрации, исправлена или снята; создание карточки само по себе не отправляет письмо |
| Повторная вакцинация | За 7 дней, за 1 день, в дату процедуры, один раз после просрочки |
| Допуск к мероприятию | Текущие проверки впервые пройдены, затем соответствие потеряно или восстановлено |
| Заявка на вязку | Одобрение, отклонение, отмена, возврат решения на рассмотрение |
| Мероприятие | За календарный день до участия, перенос времени/площадки, отмена |
| Результат | Внесение, исправление, отмена; без свободных комментариев эксперта |
| Документ | Сохранён первый или новый файл; создание строки реестра без файла не означает готовность |

Получатели имеют подтверждённый email, активный аккаунт, включённый профиль
owner и активное членство. Для фоновых писем не нужны вход или активная сессия;
выбранный сейчас профессиональный профиль не мешает уведомлениям владельца.
Все текущие совладельцы собаки рассматриваются отдельно. Для людей без собаки
получатель — сам зарегистрированный участник. Общей рассылки календаря нет.

Документы направляются личному получателю; для документа собаки он также должен
оставаться её текущим владельцем. Клубные общие формы и временные экспорты
отчётов не рассылаются. В письмах нет вложений, медицинского текста, произвольных
причин решений, JWT, чужих контактов или списков участников.

Адресат и источник проверяются повторно непосредственно перед SMTP. Блокировка,
отключение owner, неактивное членство, смена владельца или утрата основания
переводят неподходящее задание в suppressed. После приёма письма SMTP уже нельзя
отозвать его из почтового ящика; проверка относится к моменту перед отправкой.
Старое историческое событие не рассылается новым владельцам или новым аккаунтам.
Актуальные предстоящие напоминания могут получить текущие владельцы.

## Вакцинация

Срок напоминания — сохранённая `next_date`, а не медицинская `valid_until`.
Параметры препарата и старые даты не пересчитываются при изменении справочника.
Пропущенные за время остановки стадии сворачиваются в одну текущую: например,
после запуска за три дня до процедуры приходит одно актуальное напоминание,
затем за день, в дату и один раз после неё. Календарь вакцинации — UTC.
Количество оставшихся дней в тексте обновляется перед фактической отправкой.

Новая запись тем же препаратом завершает напоминания по прежней записи этого
препарата. Сравниваются дата процедуры и ID при равных датах. Отмена последующей
записи не возобновляет старые напоминания автоматически.

При переходе на другой препарат ветеринар вносит медицинскую связь одновременно
с новой прививкой:

```json
{
  "date": "2026-10-17",
  "vaccine_type_id": 2,
  "replaces_vaccination_ids": [15, 18]
}
```

Это дополнение существующих POST/PUT `/api/v1/dogs/{dogID}/vaccinations[...]`.
Отдельной команды отправки писем и отдельного маршрута выключения нет.
Связь означает замену для напоминаний; она не отменяет старую прививку,
не меняет её срок действия и не подменяет основание медицинского допуска.

До 100 разных положительных ID; прежние записи относятся к той же собаке,
датированы не позднее новой. Самоссылки/циклы и правка старой даты позже
заменяющей процедуры запрещены. При PUT пропуск поля (также null) сохраняет
связи, `[]` явно очищает их. Остальные поля PUT, `version`, `reason` и ограничение
исправления автором остаются прежними. Непустые связи возвращаются при чтении
и сохраняются в veterinary_changes. Пустые поля опускаются: новая миграция
сама по себе не меняет старые канонические снимки PDF.

Допуск к мероприятию проверяется действующими правилами events/veterinary:
возраст/класс, идентификатор, представитель, медицина на весь период и
экспертное подтверждение, если оно нужно. Письмо сообщает текущий результат
проверки, а перед явкой проверка выполняется снова. Для напоминания за день
используется часовой пояс мероприятия и время конкретного слота, если он задан.

## Хранение и фоновая обработка

Миграция 00012 создаёт `notification_event`, `notification_delivery`,
`notification_watch`, `vaccination_reminder_replacement`. Down отказывается
удалять накопленные события, задания, состояние проверок или медицинские связи.
Исходный SQL из пакета документов не исполняется.

Producer сохраняет событие и получателей в той же транзакции, что бизнес-факт
и его историю. Ошибка записи в outbox откатывает бизнес-операцию. SMTP выполняет
фоновой обработчик после commit; ошибка SMTP бизнес-факт не откатывает.

Внутри одного Go-сервера обработчик запускается сразу и затем каждую минуту.
За цикл — до 100 исходных записей на сканер и до 20 доставок, общий таймаут
цикла 45 секунд. Курсоры в PostgreSQL обеспечивают продвижение по большим
спискам после перезапуска. Исторические регистрации/решения/документы не
восстанавливаются из старой истории; текущие сроки вакцинаций и предстоящие
участия проверяются, в том числе для ранее созданных записей.

Фоновые проекции работают через публичные сервисы в транзакции с общей защитой
авторизации, без фиктивного аккаунта администратора. Политика HTTP-доступа
сохраняется. SMTP выполняется вне этой транзакции и блокировки.

Задание захватывается с lease на минуту и случайным токеном попытки. После
сбоя lease может забрать другой процесс; завершение старой попытки не перепишет
новую. Повторные попытки — через 1, 5, 15 минут, затем каждый час до потери
актуальности. Секреты, адресаты и тела писем не логируются. Стабильный
`Message-ID` относится к событию и получателю. При потере подтверждения приёма
SMTP возможен редкий повтор: exactly-once для внешнего SMTP не гарантируется.
При остановке HTTP завершается, обработчик отменяется и присоединяется до
закрытия пула БД.

Статусы доставок: pending, sending, sent, suppressed. Для локальной диагностики
достаточно агрегатов без чтения персональных данных:

```sql
SELECT status, count(*) FROM notification_delivery GROUP BY status;
SELECT count(*) FROM notification_delivery
WHERE status='pending' AND attempts>0;
```

## Проверка

После загрузки локального окружения и при работающих PostgreSQL/Mailpit:

```sh
go test ./...
go vet ./...
go build ./...
DOGCLUB_TEST_DATABASE_URL="$DATABASE_URL" DOGCLUB_TEST_MAILPIT=1 \
  go test -race -tags=integration ./...
```

Интеграционные тесты создают отдельные случайно названные БД и удаляют только
их. Опция Mailpit отправляет синтетическое письмо локальному получателю.
Для рабочей БД миграцию выполняют явно: `go run ./cmd/migrate up`, затем
`go run ./cmd/api`. API никогда не запускает миграции сам.

Ручная проверка: подтвердить дату регистрации тестовой собаки с активным
владельцем, дождаться ближайшего цикла и открыть Mailpit. Ветеринару достаточно
внести прививку с настроенными периодами препарата; дальнейшие напоминания
формирует сервер.
