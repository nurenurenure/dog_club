# Аудит PostgreSQL и эволюция схемы

## Основания и границы

Первичный аудит: 16 октября 2026 года. В начальной схеме исправлены ошибки
исполнения и базовой целостности, имена нормализованы в snake_case. Изменения
предметной модели оформлены отдельными миграциями.

При проектировании использовались отдельно предоставленные документы задания.
Они не включены в репозиторий и не требуются для запуска приложения:

- `02_database_design_and_sql.pdf`, страницы PDF 2–3 — диаграммы,
  4 — настройки ссылочной целостности, 4–20 — исходный SQL.
- `03_current_domain_description.pdf`, страницы PDF 2–5 — актуальная
  семантика идентификаторов, документов, ветеринарии, мероприятий и племенной работы.
- `01_technical_assignment.pdf`, страницы PDF 7, 13–14 — поля
  контактов, роли пользователей и активное/неактивное членство.
- `02_sql_extracted_REFERENCE_ONLY.sql` — помощник для сверки и воспроизведения
  ошибок; файл не используется как миграция и не изменялся.

Изображения PDF были просмотрены при подготовке проекта. При переносе сохраняются
33 таблицы, колонки, типы, nullability, существующие составные PK и все 31 исходный
FK. `serial`, `timestamp(6)` без часового пояса и настройки autovacuum сохранены.
В исходном отчёте указана PostgreSQL 12; приложение использует PostgreSQL 18.

## Фактическое воспроизведение исходного SQL

Проверка выполнена в отдельном одноразовом контейнере PostgreSQL
`18.6 (Debian 18.6-1.pgdg13+2)`. Для сбора всех ошибок psql запускался с
`VERBOSITY=verbose`, `ON_ERROR_STOP=off`, только на этой тестовой БД.
Получены ровно 19 ошибок:

| SQLSTATE | Сообщение PostgreSQL | Количество |
| --- | --- | ---: |
| 42P07 | `relation "IX_" already exists` | 11 |
| 42P07 | `relation "IX_имеет" already exists` | 5 |
| 42P07 | `relation "IX_проводит" already exists` | 1 |
| 42710 | `constraint "has" for relation "Club_member" already exists` | 1 |
| 42710 | `constraint "has" for relation "Document" already exists` | 1 |

При продолжении после ошибок все 33 таблицы создаются, но часть индексов и два
FK не создаются. Это не успешное развёртывание схемы. Кавычки и разделители
SQL сверены с PDF; перестановки скобок/`;` при извлечении текста не считаются
ошибками оригинала. Тестовый контейнер и его временный volume удалены.

## Исправления исходной схемы

### Исполнение и имена

- Все физические имена таблиц приводятся к нижнему регистру snake_case, без
  переименования уже существующих колонок. Точное соответствие приведено ниже.
- PK именуются `pk_<table>`, FK — по таблице и колонке, индексы —
  `idx_<table>_<column>`. Конфликты исходных имён устранены.
- Все 23 явных исходных индекса сохранены под новыми именами. Дополнительно
  созданы три индекса для обратного поиска по связующим таблицам.

### Целостность

| Таблица | Дополнение |
| --- | --- |
| dog | `UNIQUE(dog_identifier_number)`; миграция 00001 допускает NULL, миграция 00005 добавляет NOT NULL |
| dog_club_member | PK `(dog_id, club_member_id)`; два FK |
| title_dog | PK `(title_id, dog_id)`; два FK |
| veterinary_examination_disease | PK `(veterinary_examination_id, dog_id, disease_id)`; два FK |

В последней таблице FK `(veterinary_examination_id, dog_id)` ссылается на составной
PK осмотра. Это исключает диагноз, привязанный к осмотру другой собаки.
Уникальность номера собаки глобальна для всех типов идентификатора и сравнивает
хранимое значение. В миграции 00001 несколько NULL разрешены. После миграции 00005 регистрация
без номера запрещена, добавлены NOT NULL и проверка непустого номера без краевых
пробелов; API сохраняет ведущие нули. Проверки официального допуска — отдельно.

Все исходные `ON DELETE` и `ON UPDATE` сохранены. Для новых FK:

- dog_club_member: удаление собаки или члена клуба удаляет соответствующую связь;
- title_dog: удаление собаки удаляет связь; используемый титул удалить нельзя;
- veterinary_examination_disease: удаление осмотра удаляет его диагнозы;
  используемое заболевание удалить нельзя;
- изменение ключей всех новых FK ограничено `ON UPDATE RESTRICT`.

Итого в новой схеме 33 PK, 37 FK, одно дополнительное UNIQUE и 26 явных индексов
(плюс индексы, создаваемые PostgreSQL для PK/UNIQUE). В PostgreSQL 18 ограничения
NOT NULL также видны в pg_constraint с типом `n`; их нельзя считать PK/UNIQUE/FK.

## Миграции и наполнение

- `00001_initial_schema.sql` создаёт согласованную схему, Down удаляет только
  её таблицы в порядке зависимостей без `DROP ... CASCADE`.
- `00002_seed_dictionaries.sql` содержит 68 записей в 17 справочниках. Полный
  список, происхождение и базовые значения проекта — в `seed-catalog.md`.
- vaccine_type не содержит начальных записей. Подтверждённые препараты
  и два периода в days/months добавляются через ветеринарный API.
- Данные людей, собак и процессов не создаются. Начальные ID не определяют
  бизнес-правила; serial-последовательности синхронизированы после заполнения.
- Down начального наполнения удаляет только его ID. Если на них есть ссылки,
  PostgreSQL отклоняет откат; вся seed-миграция откатывается транзакционно.

Команда `cmd/migrate` использует Goose и pgx/stdlib; API сохраняет pgxpool.
SQL встроен в бинарный файл. Автоматического запуска миграций из HTTP-сервера нет.
Изменения миграций сериализуются advisory lock PostgreSQL. Первое `up` отказывается
работать с непустой схемой public без истории Goose. Это не средство переноса
данных из старого учебного SQL. `status` на новой БД не создаёт служебных таблиц.

## Проверки и наблюдения

Интеграционные тесты создают БД со случайным именем на предоставленном тестовом
сервере и удаляют только созданные БД. База, указанная в тестовом URL, не мигрируется.
Проверяются создание, повторное up, status, откат обеих версий и повторное создание;
число таблиц/FK и строк справочников; последовательности, дубликаты, сироты,
составная ссылка осмотра, CASCADE/RESTRICT, защита существующей БД и атомарность
отката seed при наличии ссылок.

В PostgreSQL 18.6 попытки вставить отсутствующую ссылку дают SQLSTATE `23503`,
а проверенные удаления с `RESTRICT` — `23001`. Это разные коды ограничений;
SQLSTATE не преобразуются универсально в HTTP-статус, а обрабатываются
в контексте предметного сценария.

Все перечисленные проверки завершились успешно, включая `-race`, настоящий CLI,
полный откат и повторное применение. Рабочая локальная БД затем создана отдельно:
обе миграции применены, присутствуют 33 прикладные таблицы и история Goose,
68 начальных записей; vaccine_type пуст. API на этой БД вернул ready=200 и
завершился по SIGTERM с кодом 0. Рабочие контейнер и volume сохранены.

## Текущее состояние модели и ограничения

| Тема | Реализация и ограничения |
| --- | --- |
| Авторизация | Аккаунты и профили в auth; карточка члена не является источником ролей доступа |
| Родители | Необязательные FK и внешние сведения в родословной; внешнего каталога нет |
| Карточки собак | Регистрация с идентификатором и владельцем; черновиков нет |
| Ветеринария | Наследственность диагноза, два периода препарата, история, медицинские заключения |
| Племенная работа | Заявки, решения, вязки, помёты, щенки и проверки пары |
| Мероприятия | Заявки, классы участия, площадки event_venue; возможны участники без собаки |
| Документы | Реестр, закрытые файлы, реквизиты выдачи, печатные формы и снимки источников |
| История | Физическое удаление собак, клинических и племенных фактов не реализовано; наследуемые CASCADE требуют аудита перед добавлением удаления |
| Проверки | Даты, пол, родство, медицинские и процессные ограничения проверяются предметными сервисами |

В начальной миграции сохраняются исходные типы ID/времени и составные PK.
Новые предметные связи и ограничения вводятся следующими миграциями.

## Миграция 00003: авторизация

Миграция `00003_auth.sql` добавляет учётные записи, профили и сессии.
Она не меняет первые две миграции и не удаляет исходные данные. Добавлены
семь таблиц авторизации, 12 FK и стабильные уникальные коды шести существующих
ролей. Итого: 40 прикладных таблиц, история Goose и 49 FK. Значения 68 строк
справочников сохранены; новых словарных значений нет.

Аккаунт `users` может иметь несколько `user_profiles`, один профиль на роль.
Сессия содержит один активный профиль; составной FK `(profile_id, user_id)`
исключает привязку сессии к чужому профилю. Необязательный уникальный
`users.club_member_id` связывает аккаунт с карточкой, но `club_member.role_id`
не предоставляет права. Auth-таблицы используют timestamptz и непрозрачные text ID;
типы существующих предметных таблиц сохранены.

Новые связи имеют ON DELETE RESTRICT. Секреты приглашения/refresh/восстановления
хранятся как SHA-256 проверочные значения, пароли — Argon2id. Журнал событий
фиксирует ID исполнителя/цели, тип, время и request_id без исходных секретов.
Откат третьей версии удаляет только auth-модель и role.code, поэтому проверялся
исключительно на одноразовых БД. Роли и первоначальное наполнение после отката
сохраняются. Полный down/up трёх версий и ограничения прошли интеграционные тесты.

Модель аккаунтов, блокировки, переключение профиля, защита последнего admin
и правила дальнейшего использования описаны в [auth.md](auth.md).

## Миграция 00004: члены клуба

Поле club_member.role_id удаляется: роли доступа принадлежат профилям аккаунта.
Перед подготовкой миграции рабочая БД проверена запросами
счётчиков: карточек и старых значений роли нет, зависимых представлений нет,
есть один ожидаемый FK. Исходный пакет и первые три миграции не менялись.

`00004_members.sql` удаляет колонку и её FK (индекс колонки PostgreSQL удаляет
автоматически), добавляет version, расширяет contact_value с 50 до 254 символов
и создаёт member_changes с тремя RESTRICT FK на карточку, аккаунт и профиль
исполнителя. Итого: 41 прикладная таблица, история Goose и 51 FK.
Составной PK contact и остальные предметные связи сохранены. Добавлены индекс
контактов по карточке и индекс истории по карточке/порядковому номеру.

Роли, статусы и прочие 68 значений справочников не удаляются и не добавляются.
Наличие старой роли не создаёт аккаунт или профиль. Обновление существующей
карточки с ролью проверено на одноразовой БД: карточка и её поля сохраняются,
старое поле удаляется, аккаунтов и профилей не появляется.

Down четвёртой версии допускается только на пустом каталоге членов, поскольку
удалённые значения роли нельзя восстановить автоматически. С непустым каталогом
Down отказывается транзакционно; это проверено тестом сохранности схемы и данных.
Полный down/up четырёх версий проверен на пустой одноразовой БД.

Миграция 00004 сохраняет адреса в общей таблице address. Members запрещает
изменять/удалять используемый мероприятием адрес. Миграция 00008 добавляет
отдельные площадки event_venue, сохраняя возможность использовать старые адреса.
Политика доступа, история и ограничения типов даты
описаны в [members.md](members.md).

После успешных проверок миграция применена к рабочей локальной БД: четыре
версии applied, 42 таблицы с историей Goose, 51 FK. Карточек, аккаунтов и записей
member_changes нет. API вернул readiness 200 и корректно завершился по SIGTERM.

## Миграция 00005: собаки

Перед изменением рабочей локальной БД прочитаны счётчики: собак, родословных,
пропущенных идентификаторов, повторных родословных и отсутствующих родителей нет.
Исходный пакет и первые четыре миграции сохранены без изменений.

`00005_dogs.sql` вводит NOT NULL и CHECK непустого номера идентификатора,
сохраняя глобальное UNIQUE. Добавляет положительные numeric(7,2) height_cm
и weight_kg, а также version bigint. У родословной одна запись на собаку, родители необязательны
и имеют RESTRICT FK на dog. Добавлены отдельные номер/организация родословной
и внешние сведения каждого родителя. CHECK запрещает самоссылку, одинаковых
известных родителей, одновременную ссылку и внешнее описание, организацию без
имени/номера. Пол, даты и циклы проверяет Service внутри общей транзакции.

Внешние сведения не создают отдельное животное и не связываются автоматически.
Связь на зарегистрированную собаку устанавливает сотрудник явно; прежний текст
остаётся в истории. В title_dog добавлены необязательные awarded_on и basis;
составной PK сохранён. Титулы не истекают автоматически. Исправление ошибочной
записи требует причины и истории; лишение официального титула не реализовано.

Новая dog_changes имеет три RESTRICT FK на собаку и исполнителя, снимки до/после
и индекс по собаке/ID изменения. Индексы родителей обеспечивают поиск потомков.
Итого после пятой миграции: 42 прикладные таблицы, история Goose и 56 FK.
Справочники не меняются; личные данные и карточки не добавляются.

Тесты на PostgreSQL 18.6 проверили Up/Down всех пяти версий, NOT NULL/CHECK/FK,
отказ Up при старом NULL-идентификаторе, отсутствующем родителе и повторных
родословных. Ошибка откатывает всю миграцию и сохраняет старые данные. Никаких
выдуманных номеров и фиктивных родителей для прохождения миграции нет.
Down требует пустого каталога собак: старую модель нельзя безопасно восстановить
с новыми внешними сведениями и историей. Отказ с непустым каталогом также проверен.

API физического удаления собаки не предоставляет. Старые каскады остальных
таблиц не менялись; удаление потребует отдельного плана сохранения медицинской
и прочей истории. Контракт и ограничения — в [dogs.md](dogs.md).

После успешных проверок пятая миграция применена к рабочей локальной БД:
пять версий applied, 43 таблицы с историей Goose, 56 FK. Собак, членов клуба
и аккаунтов нет. Проверены readiness 200, безопасные ошибки/логи и SIGTERM=0.

## Миграция 00006: ветеринария

Медицинские сведения вводит ветеринар. Сроки рассчитываются автоматически
по двум независимым периодам препарата в днях/календарных месяцах.
Решение о допуске принимается отдельно, с проверкой выбранных вакцинаций. До подготовки миграции
прочитаны рабочие счётчики: осмотров, вакцинаций, препаратов и диагнозов нет.
Первые пять миграций и исходные PDF/SQL сохранены.

`00006_veterinary.sql` сохраняет составные PK осмотров и вакцинаций. Добавляет
nullable is_hereditary у диагноза, единицы validity_period, отдельный период
revaccination с единицей и version препарата. Старый период без единицы не
получает вымышленную трактовку. Новые настроенные периоды положительны,
единицы ограничены days/months. Согласованные 68 справочных строк не меняются.

В осмотрах и вакцинациях добавлены авторы, version и is_void; в вакцинациях —
снимок препарата, дата окончания действия и исполнитель-человек. Старые авторы
остаются NULL, даты/время и следующая процедура сохраняются, неизвестная
наследственность остаётся NULL. После изменения каталога ранее сохранённые
сроки вакцинаций не пересчитываются автоматически.

Добавлены veterinary_clearance (отдельные назначения events/breeding),
clearance_vaccination и veterinary_changes. Составные FK заключение/осмотр/собака
и заключение/вакцинация/собака не допускают основание от другого животного.
Всего добавлены 3 таблицы и 13 FK: 45 прикладных таблиц, Goose и 69 FK.
Добавлены индексы по собаке, назначению, основаниям и истории.

Обязательность выбранных оснований, даты и права проверяет Service в общей
auth-транзакции. Физического удаления клинических записей через API нет;
ошибочная запись получает is_void с причиной и историей. Изменение даты рождения
защищено публичной DogDatesPolicy, без межмодульного SQL в dogs.

На PostgreSQL 18.6 прошли полный Up/Down шести версий, проверки ключей и
сохранности старых клинических данных. Down шестой версии отказывается при
осмотрах/вакцинациях/заключениях/истории или настроенных препаратах; ошибка
транзакционно сохраняет схему и значения. API, границы и формулы — в
[veterinary.md](veterinary.md).

После успешных проверок миграция применена к рабочей локальной БД: шесть
версий applied, 46 таблиц с Goose и 69 FK. Людей, аккаунтов, собак и медицинских
процедур/препаратов нет. API вернул readiness 200 и завершился по SIGTERM с кодом 0.

## Отчётность без изменений схемы

Новых миграций, таблиц, справочных значений и зависимостей нет. Периодный отчёт
читает агрегаты через публичные сервисы в одной WithAccess-транзакции; SQL
остаётся в репозиториях members/dogs/breeding/events. Модуль reports не получает
персональные карточки, медицинские снимки или приватные репозитории.

Известные предметные даты считаются по обеим включительным границам. Статусы
членства/собаки не исключают вступление/регистрацию из прошлого периода.
Для мероприятий нужен completed и местная дата окончания; неизвестная зона
не заменяется часовым поясом БД. Вязки только проведённые, щенки — сумма общего
количества в помётах по дате рождения. Текущие итоги и полнота дат отдельно,
не выдаются за исторический состав клуба. Даты по аудиту не угадываются.

JSON/PDF/CSV формируются без архива, записей document/document_file и файлов
в DOCUMENTS_DIR. Исправления исходных фактов меняют новый расчёт. Скачанные
пользователем файлы не переписываются. Перед выдачей экспорта повторяются права.

Полный прогон с -race, go vet, сборка и go mod verify прошли. Проверены границы,
високосный день, часовые пояса, старые неполные записи, исключение двойного счёта,
согласованное чтение, исправления, профили/блокировки, HTTP и совпадение JSON/CSV.
PDF просмотрены визуально, включая пятистраничный тестовый отчёт. Собранные
migrate/admin/API с Mailpit прошли реальный сценарий трёх форматов; одноразовая
база удалена, файлов/архива не создано, секретов в логах нет.

Рабочая схема без изменений: 11 applied, 59 таблиц с Goose, 110 FK; аккаунтов,
людей, собак, мероприятий, документов и файлов нет. API: readiness 200,
отчёты без входа 401, безопасные логи, SIGTERM=0. Методика и ручной сценарий —
[reports.md](reports.md).
