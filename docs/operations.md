# Локальная эксплуатация backend

Репозиторий содержит Go API, PostgreSQL 18 и Mailpit. React-клиент не включён.
Развёртывание на публичном сервере, внешний SMTP, TLS, Prometheus/Grafana,
ELK, Telegram, REST-ящик уведомлений и WebSocket не настроены.

## Первый запуск и обычная работа

Нужны Docker Engine/Desktop и Compose с `up --wait`, `service_healthy` и
`service_completed_successfully`. Go на компьютере для Docker-режима не нужен.
Из корня backend скопируйте `.env.example` в `.env`, если своего файла ещё нет.
Задайте случайные `POSTGRES_PASSWORD` (URI-safe hexadecimal) и `AUTH_JWT_KEY`
(base64 минимум 32 случайных байт). Существующую `.env` не заменяйте примером.
Секреты остаются в локальной `.env`, не в образе или Git. Не публикуйте вывод
`docker compose config` без `--quiet`: он содержит подставленные секреты.

```sh
docker compose config --quiet
docker compose up --build
```

Либо фоновый режим: `docker compose up --build -d --wait api`. PostgreSQL должен
стать healthy, затем одноразовый `migrate` применяет только отсутствующие
миграции и проверяет все зарегистрированные файлы. После успешного завершения
запускается API. Сам API миграций не выполняет. Набор миграций не изменён: 00001–00013.
Существующий `dogclub_postgres_data` сохраняется. Не выполняйте `down --volumes`
для рабочего проекта: это удалит постоянные данные.

- API: `http://127.0.0.1:8080`, опубликованный порт меняется через `API_PORT`.
- Mailpit: `http://127.0.0.1:8025`, SMTP на компьютере `127.0.0.1:1025`.
- PostgreSQL на компьютере `127.0.0.1:5432`.
- Все опубликованные порты привязаны только к `127.0.0.1`.
- Внутри сети Compose API слушает `0.0.0.0:8080`, БД — `db:5432`, SMTP —
  исключительно `mailpit:1025`. Явный `LOCAL_COMPOSE=true` разрешает этот
  локальный маршрут и HTTP-cookie без Secure. Origin-проверка остаётся включена.
  Этот Compose не предназначен для публикации в интернет.
- Для запуска Go на хосте сохранён прежний режим: `LOCAL_COMPOSE=false`,
  loopback-адреса из `.env`, см. README. Одновременно два API-процесса не запускайте.

Первый администратор создаётся приглашением; пароль не генерируется и не печатается:

```sh
docker compose run --rm --no-deps --entrypoint /admin api bootstrap admin admin@dogclub.test
```

Код из локального Mailpit используется в `POST /api/v1/auth/activate`, затем
`POST /api/v1/auth/login`. Подробности и JSON-примеры — в `docs/auth.md`.
Дополнительные команды:

```sh
docker compose run --rm --no-deps --entrypoint /migrate api status
docker compose exec api /maintenance
curl -fsS http://127.0.0.1:8080/health/live
curl -fsS http://127.0.0.1:8080/health/ready
docker compose stop api
docker compose up -d --wait api
```

Процесс работает как UID/GID 65532. Приватные файлы — том `documents_data`,
каталог `/data/documents` с mode 0700, новые файлы 0600. В образе нет пользовательских
файлов. Образ собирается в несколько стадий; SDK остаётся только в стадии проверок.
Имена рабочих томов зависят от Compose project name; не меняйте его случайно.

## Переход с каталога документов на компьютере

Если в рабочей БД уже есть `document_file`, а новый Docker-том пуст,
`migrate` откажется запускать API. Это защищает от тихой потери доступа к копиям.
Остановите также старый API на хосте, сделайте копию прежнего каталога и выполните:

```sh
scripts/import-documents.sh /absolute/path/to/old/documents
docker compose up -d --wait api
```

Скрипт принимает только абсолютный существующий каталог и пустой целевой том,
копирует файлы, выставляет приватные права и сверяет каждый зарегистрированный
файл с размером/SHA-256 в БД. Исходный каталог сохраняется. При ошибке API остаётся
остановлен; не очищайте целевой том автоматически, сначала разберите причину.

## Резервная копия

Для скриптов нужны POSIX sh, Docker Compose и `shasum` (штатно в macOS;
в Linux пакет Perl/Digest::SHA). Копии содержат персональные данные: храните их
в закрытом каталоге и отдельно резервируйте ключи/`.env`. Архивы не шифруются самим
скриптом; при переносе используйте защищённое хранилище. `.env` в копию не включается.

Перед копированием завершите другие процессы, пишущие в эту БД/каталог: host API,
CLI-изменения, ручные SQL. Скрипт рассчитан на согласованную архитектуру с одним
API, не на произвольных внешних писателей. Не запускайте одновременно Compose up,
миграции, импорт и резервирование. Скрипты backup/import используют локальную
блокировку `var/maintenance.lock`.

```sh
mkdir -p var/backups
scripts/backup.sh /absolute/path/to/backend/var/backups/2026-10-17
```

Каталог назначения должен отсутствовать. Скрипт корректно останавливает HTTP и
worker, проверяет файлы и сохраняет согласованную пару: custom-format `pg_dump`
и `documents.tar` из остановленного приложения. Затем пишет `storage.json`
(версия миграций, число таблиц, файлов, байтов и сводный хеш зарегистрированных
ключей/размеров/хешей), версию PostgreSQL, ID образа, `SHA256SUMS` и маркер `COMPLETE`.
Каталог 0700, файлы 0600. Копии без `COMPLETE` не пригодны для восстановления.
Временный дамп может быть большим: заранее проверьте место.

Если API работал, trap запускает его обратно даже при ошибке копирования.
Если до копирования он был остановлен, таким и останется. Скрипт сообщает сбой
перезапуска; после него явно проверьте `/health/ready`. Рабочие тома не удаляются.
Один успешный `pg_dump` ещё не доказывает пригодность копии: проверяйте восстановление.

## Проверка восстановления — только в новый проект

Нужны прежние секреты отдельно от архива; в тесте восстановления используйте
свободные порты. Скрипт запрещает имя `dogclub`, существующие контейнеры и тома
целевого проекта. Рабочая БД не перезаписывается.

```sh
export API_PORT=18080 POSTGRES_PORT=15432 MAILPIT_SMTP_PORT=11025 MAILPIT_HTTP_PORT=18025
scripts/restore.sh /absolute/path/to/backup dogclub_restore_check
export COMPOSE_PROJECT_NAME=dogclub_restore_check NOTIFICATIONS_ENABLED=false
curl -fsS http://127.0.0.1:18080/health/ready
docker compose exec api /maintenance
```

До создания проекта проверяются `COMPLETE` и контрольные суммы. В новый пустой
PostgreSQL восстанавливается дамп; в новый том — документы. Полная проверка всех
зарегистрированных файлов и сравнение `storage.json` обязательны до старта API.
API стартует с **`NOTIFICATIONS_ENABLED=false`**: сканирование/доставка выключены,
сохранённая очередь не удалена. Оставляйте эту переменную false при последующих
Compose-командах восстановленного проекта, чтобы не включить доставку случайно.
Новые бизнес-операции по-прежнему могут добавлять outbox-события.

Проверьте вход, права и скачивание реального документа. При проверках с настоящей
копией данные доступны только локально. Для проверки восстановления выбирайте
доверенные архивы, созданные этим инструментом. При несовпадении хешей API не
запускается; частично созданный тестовый проект сохраняется для диагностики.
Удалять его можно только после проверки имени проекта и отсутствия нужных данных:

```sh
# Только одноразовый восстановленный проект, никогда рабочий dogclub!
docker compose -p dogclub_restore_check down --volumes
unset COMPOSE_PROJECT_NAME NOTIFICATIONS_ENABLED API_PORT POSTGRES_PORT MAILPIT_SMTP_PORT MAILPIT_HTTP_PORT
```

## Метрики и диагностика

`GET /api/v1/operations/metrics` доступен только активному профилю `admin` с Bearer
JWT. Права повторно проверяются в БД, в том числе перед выдачей результата.
Другим профилям — 403, без входа — 401; параметры запроса — 422.

JSON содержит uptime, HTTP по методу и шаблону маршрута (число запросов,
4xx/5xx, сумма и максимум длительности в секундах), состояние pgxpool,
число pending/sending/sent/suppressed доставок и время последнего успешного цикла
worker в Unix seconds. Текущий запрос метрик учитывается после его завершения.
HTTP-счётчики и время цикла обнуляются при старте процесса; 0 означает, что
успешного цикла с запуска не было. Состояния очереди читаются из PostgreSQL.
Успешный цикл означает завершение обработки страницы/доставок, а не отсутствие
pending: отдельная SMTP-ошибка сохраняется на повторную попытку. Рост pending
нужно оценивать вместе с состоянием Mailpit и числом попыток при диагностике.

В ответах и логах нет получателей, email, токенов, текстов клиники, тел запросов,
сырых ID в URL и query strings. Не передавайте JWT в URL. Для диагностики:

```sh
docker compose ps
docker compose logs --tail=100 api
```

Docker-healthcheck проверяет liveness; отдельно readiness возвращает 503 при
недоступной БД и восстанавливает 200 после её возвращения. Недоступность БД не
делает живой процесс неисправным. SIGTERM даёт HTTP завершить активные запросы,
останавливает и дожидается worker, затем закрывает пул; Compose выделяет 30 секунд.
Долговременную доступность 99% локальный smoke-тест не подтверждает.

## Проверки без Go на компьютере

```sh
# Создаваемые интеграционными тестами БД имеют случайные имена и удаляются тестами.
docker compose run --build --rm checks
# Полный Docker-сценарий: нужны Python 3 stdlib и Docker; рабочая .env не используется.
python3 scripts/verify.py
```

Первый вариант выполняет `go mod verify`, `go vet ./...`, `go build ./...`,
`go test -race -tags=integration ./...` внутри SDK. Второй создаёт собственные
проекты с отдельными томами/случайными паролями/свободными loopback-портами,
проверяет HTTP, хранилище, почту, сбои, перезапуск, backup/restore и нагрузку
50 клиентов с отдельными заранее открытыми сессиями. Ограничение входа 10/мин
сохраняется, поэтому подготовка занимает несколько минут. JSON результата —
`var/stage12-verification.json`, не Git. Тестовые ресурсы удаляются в finally;
при аварийном завершении процесса их можно найти по `dogclub_verify_*`.
Полные предметные сценарии, включая племенной учёт, проверяются интеграционными
тестами каждого модуля; HTTP smoke дополняет их проверкой работающего контейнера.
