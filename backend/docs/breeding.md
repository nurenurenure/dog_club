# Племенной учёт

Реализован процесс: заявка → проверка пары → решение эксперта → фактическая
вязка → исход/помёт → регистрация идентифицированных щенков.

Основание: ТЗ §4.5, PDF 15, M4 на PDF 26; актуальное описание предметной области,
PDF 4–5, логическая и физическая схемы второго PDF и схема третьего PDF.
Модель и ограничения миграции описаны в [аудите схемы](database-audit.md).
Клубное правило — 365 дней между рождениями помётов — основано на рекомендации РКФ.
Полное соответствие всем правилам РКФ не заявляется; исключения с сокращением интервала не реализованы.
Источник рекомендации — [пояснение РКФ об интервалах между помётами](https://help.rkf.online/ru/knowledge_base/art/2397/cat/616/pervaja-vjazka-suki-i-intervali-mezdu-pometami).

## Доступ

| Активный профиль | Чтение | Запись |
| --- | --- | --- |
| staff | Все племенные записи, проверки, история, поиск собак | Заявки, проведение, исходы, помёты, щенки, исправления |
| expert | Все племенные записи, проверки, история, поиск собак | Одобрение/отказ по ожидающей заявке |
| leader | Все племенные записи, проверки, история, поиск собак | Нет |
| owner | Заявки/вязки по текущим своим родителям; помёты по своим родителям или связанным щенкам | Нет |
| admin, veterinarian | Племенной раздел недоступен | Управление аккаунтами/медициной остаётся в своих разделах |

Права профилей не объединяются. Неактивное членство закрывает весь owner-раздел,
включая списки, историю и отсутствующие записи; аккаунт и другие профили остаются.
Владение, членство и состояние аккаунта/профиля/сессии проверяются в БД на каждом
запросе. Потеря владения немедленно закрывает соответствующие записи.
Скрытая от owner запись возвращает 404; неподходящий профиль/членство — 403.

Эксперт получает через breeding только Summary/происхождение собак, медицинский
допуск и диагнозы с наследственностью true/null, датой и ID осмотра. null означает
неустановленную наследственность. Клинические тексты, сведения об авторах осмотра,
владельцы и контакты в проверку пары не входят. Общий CRUD dogs и ветеринарный
раздел не получают новых полномочий expert.

Owner не получает assessment пары в заявке/вязке и решениях. В истории owner
получает метаданные изменения с before=null и after=null. Это предотвращает
раскрытие медицинского снимка второй собаки или прежних владельцев. Связанные
ID щенков в помёте не открывают чужие карточки dogs.

## Заявка, проверка, решение

Заявка содержит female_dog_id, male_dog_id, planned_date, nullable expected_birth_date,
comment, status, assessment и version. Даты — YYYY-MM-DD, фактические даты не
позднее текущей даты UTC. Ожидаемое рождение должно быть позже планируемой вязки.
Комментарий до 2000 символов без управляющих знаков.

Сотрудник может внести заявку до устранения проблем пары. Проверка возвращает
blocking_reasons и warnings: одобрение разрешено только без блокирующих причин.
Проверяются разные собаки, пол Сука/Кобель, одинаковая порода, идентификаторы,
рождение родителей раньше вязки и медицинский допуск обеих собак на её дату.
Неактивный статус собаки («Снята с учёта», «Умерла», «Потеряна», «Исключена»)
блокирует вязку отдельно для самки и самца: female_inactive, male_inactive.

Происхождение раскрывается по известным ссылкам dog_id; внешние сведения
остаются текстом. Близкое родство в пределах трёх поколений блокирует вязку
(лаб. 3, fn_check_breeding_relatedness), причины проверяются по порядку:

| Причина | Условие |
| --- | --- |
| parent_child | одна собака — мать или отец другой |
| shared_parent | общий родитель: полнородные и неполнородные братья и сёстры |
| common_ancestor_3_generations | общий предок не дальше прадеда у каждой собаки, включая деда/прадеда самой пары |

Более дальние общие предки, неполная родословная и диагнозы остаются
предупреждениями для решения эксперта. Автоматических запретов по конкретной
болезни, минимальному возрасту или числу помётов нет. Ограничение обхода дерева —
1000 уникальных карточек, превышение требует уточнить данные.

pedigree_known_3_generations у каждой собаки проверки (лаб. 3, fn_pedigree_depth_3)
равно true в одном из двух случаев:

- у собаки заполнены номер и организация документа родословной (pedigree.number
  и pedigree.issuer): официальная родословная содержит не меньше трёх поколений,
  а предков из других питомников нельзя завести карточками без владельца в клубе;
- без документа — родители и деды являются карточками клуба, а все прадеды известны
  карточкой или внешней записью.

Предки по документу автоматически не сверяются. Поле информационное и вязку
не блокирует; в снимках, сохранённых до версии API 0.11, его нет.

Статусы заявки: pending, approved, rejected, cancelled. Только expert переводит
pending в approved/rejected с reason/version. expected_birth_date эксперт может
уточнить при решении. Решение и полный снимок проверки сохраняются отдельно и
не переписываются. Исправление сотрудником возвращает заявку в pending и очищает
текущий assessment; предыдущие решения остаются. Отменённая или уже проведённая
заявка не редактируется. Новая заявка оформляется отдельно.

Одновременно допускается одна одобренная, ещё не проведённая заявка для самки.
Проведённая вязка с неизвестным исходом блокирует следующее одобрение до уточнения.
Отменённая заявка не считается проведённой вязкой. При отсутствии помётов в БД
возвращается earlier_litters_not_recorded, а не утверждение, что их никогда не было.

## Подбор пары

GET /api/v1/breeding/dogs/{dogID}/mate-candidates (staff, expert, leader; лаб. 3,
fn_suggest_mates) возвращает dog_id, as_of (текущая дата UTC), candidates в форме
DogSummary без владельцев и truncated. Подбор для неактивной собаки отклоняется 422.

Кандидат проходит все фильтры: другой пол, та же порода, активный статус, возраст
от 24 до 120 полных месяцев, нет неаннулированных диагнозов с is_hereditary=true
и нет близкого родства из таблицы выше. Неуточнённая наследственность (null) не
исключает кандидата: её оценивает эксперт при проверке заявки. Сука-кандидат
дополнительно не должна иметь проведённой вязки с неизвестным исходом или
одобренной непроведённой заявки, а со дня последнего рождения помёта должно пройти
365 дней. SQL-фильтр читает не более 500 собак по возрастанию ID; при превышении
truncated=true. Подбор — подсказка: заявка всё равно проходит полную проверку.

## Медицинская проверка на дату

Breeding вызывает публичный veterinary.CheckForBreeding в той же транзакции.
Выбирается последнее заключение breeding по дате осмотра и ID заключения среди
осмотров не позднее проверяемой даты. Более поздний осмотр не обосновывает прошлую
вязку. Недействительное последнее заключение включается в выборку: возврата к
старому разрешению нет. Проверяются выбранные вакцинации, даты и сроки включительно,
как в [ветеринарном учёте](veterinary.md).

Проверка использует текущее состояние медицинских записей с подходящими датами;
она не реконструирует их старые версии на прошедший момент. Сохранённый assessment
показывает сведения, использованные при принятии конкретного решения/проведении.
Наследственные/неустановленные диагнозы показываются из действующих осмотров до
проверяемой даты; автоматического вывода об излечении или запрета по ним нет.

Перед проведением проверки повторяются: одобрение не гарантирует сохранения
допуска. Фактическая дата должна совпадать с одобренной; перенос требует исправить
заявку и получить повторное решение до регистрации проведения.

## 365 дней между рождениями

Фиксированное правило первой версии: предыдущая дата рождения помёта + 365 дней.
Это дни, а не календарный год: 2024-02-29 + 365 дней = 2025-02-28.
Отдельных фиксированных интервалов между вязками или от родов до вязки нет;
срок беременности в код не зашит.

При наличии предыдущего помёта expected_birth_date обязательна для одобрения и
должна быть не раньше earliest_birth_date. Ожидаемая дата — оценка эксперта:
она не подменяет фактическую дату и не гарантирует будущий интервал.

Реальный помёт сохраняется и при интервале менее 365 дней. Ответ содержит
previous_birth_date, interval_days и interval_violation. Интервал вычисляется
между соседними зарегистрированными помётами этой самки по дате рождения и ID,
поэтому внесение/исправление старого помёта меняет текущие результаты проверки.
Первый зарегистрированный помёт имеет неизвестный предыдущий интервал, null.
Условные даты прошлых помётов из старого счётчика щенков не создаются.

## Вязка, помёт, щенки и исправления

POST perform создаёт одну проведённую breeding на заявку и увеличивает версию
заявки. Планирование хранится в заявке; искусственная проведённая запись до
подтверждения сотрудником не создаётся. Результат: unknown, no_litter либо litter.
Вязка и помёт — факты, последующее истечение допуска их не отменяет.

Сотрудник уточняет исход через PUT breeding с version/reason. Исход litter должен
соответствовать наличию помёта, который создаётся отдельной операцией. У старых
записей без заявки дата не изменяется без отдельного согласования переноса данных.
Время старой breeding_date сохраняется при передаче той же календарной даты.

Одна breeding связана максимум с одним помётом. Дата рождения позже вязки,
родители старше потомства, количество щенков положительное. no_litter — отдельный
исход, ноль щенков не создаёт фиктивный помёт. Число щенков нового учёта хранится
только в litter.total_puppies. breeding_number_of_puppies остаётся историческим,
возвращается как legacy_puppy_count и не редактируется через новый API.

Щенок регистрируется обычной карточкой с обязательным уникальным строковым
идентификатором и существующими владельцами. Дата рождения, порода и родители
берутся из помёта. Карточка, владельцы, родословная, dog_changes, связь и история
помёта записываются атомарно. Ответ — помёт с актуальными dog_ids.

Существующую карточку можно связать, передав version помёта и dog_version.
Дата рождения/порода должны совпадать. Отсутствующие родители заполняются из
помёта; противоречащие ссылки или внешние сведения не заменяются автоматически.
Одна карточка входит максимум в один помёт, число связанных карточек не больше
total_puppies. Удаление ошибочной связи требует version/reason, сохраняет карточку
и её родословную; исправления карточки выполняются отдельно по правилам dogs.

Нельзя уменьшить количество ниже числа связанных карточек или изменить дату
помёта при связанных щенках. Ошибочные связи сначала явно исправляются.
Публичная DogPolicy не позволяет сменить дату рождения/родителей связанного щенка,
породу участника проведённой вязки либо его пол/дату рождения так, чтобы они
противоречили зарегистрированному факту. Физического удаления записей API нет.

Все изменения проверяют version, исправления требуют reason до 500 символов.
breeding_changes хранит before/after, исполнителя, request_id и время. Ошибка
истории откатывает всю операцию. Все обращения идут через auth.WithAccess в общей
транзакции и под существующей advisory lock; внешнее I/O под ней не выполняется.
Приватные репозитории других модулей не используются, циклических импортов нет.

## API и ручная проверка

Добавлены 23 операции под /api/v1; полная спецификация — [OpenAPI](../api/openapi.yaml).
Основные маршруты:

| Маршрут | Операции |
| --- | --- |
| /breeding/dogs | GET поиск собак без владельцев: staff/expert/leader |
| /breeding-requests | GET список, POST новая заявка |
| /breeding-requests/{id} | GET запись, PUT исправление |
| /breeding-requests/{id}/check | GET текущая проверка пары |
| /breeding-requests/{id}/decisions | GET решения, POST решение эксперта |
| /breeding-requests/{id}/cancel | POST отмена |
| /breeding-requests/{id}/perform | POST проведение |
| /breedings, /breedings/{id} | GET список/запись, PUT уточнение записи |
| /litters, /litters/{id} | GET список/запись, POST создание, PUT исправление |
| /litters/{id}/puppies | POST регистрация карточки щенка |
| /litters/{id}/puppies/link | POST связь существующей карточки |
| /litters/{id}/puppies/{dogID}/unlink | POST исправление связи |
| /breeding-requests/{id}/history, /breedings/{id}/history, /litters/{id}/history | GET история |

Списки: records/next_after, after>=0, limit=1..100 (по умолчанию 50), dog_id для
связанных собак. Поиск /breeding/dogs: q, breed_id, after, limit. Доступ owner
фильтруется до пагинации. 201+Location возвращают создание заявки, проведение
и создание помёта; остальные команды возвращают 200 с актуальным объектом.
Строгий JSON до 16 КиБ, RFC 9457, breeding_conflict 409 и breeding_unavailable 503.
SQL, секреты, медицинские тексты, тела и параметры поиска в логи не попадают.

Для ручной проверки подготовьте профили/людей/собак по [auth](auth.md),
[members](members.md), [dogs](dogs.md). Ветеринару нужна связь с карточкой человека.
Под veterinarian добавьте препарат с подтверждёнными сроками, вакцинации, осмотры
и действующие заключения breeding обеих собак по [veterinary](veterinary.md).

Далее под staff создайте заявку, под expert выполните check и decisions с текущей
версией и причиной. Под staff выполните perform на одобренную дату, затем POST
litters с версией вязки. Добавьте щенка через POST puppies с версией помёта и
проверьте его parents/date через dogs. Владелец должен читать запись, получать
assessment=null и терять доступ при передаче собаки/неактивном членстве.

## Миграция и проверки

00007 добавляет 5 таблиц и 11 FK: итого 50 прикладных таблиц, Goose и 80 FK.
Исходный составной PK breeding сохранён; дополнительно введена уникальность
breeding_id для ссылок. Если старые строки имеют одинаковый ID с разными парами,
Up атомарно отказывается: строки не выбираются и не перенумеровываются молча.
Старые даты/время и счётчики сохраняются, заявки/помёты/авторы не выдумываются.
Down отказывается при наличии новой племенной информации.

```bash
go test -race -count=1 ./...
export DOGCLUB_TEST_DATABASE_URL="$DATABASE_URL"
go test -race -count=1 -tags=integration ./...
go vet -tags=integration ./...
go build -o bin/ ./cmd/...
go mod verify
git diff --check
```

Проверены PostgreSQL, полный процесс и роли, границы 364/365 и високосный год,
отзыв допуска после одобрения, медицинская проверка на дату без будущих осмотров,
отсутствие возврата старого разрешения, изменение заявки с повторным решением,
регистрация/связывание/исправление связей щенков, ограничения карточек и количества,
конкурентные версии и одобрения, полный откат при отказе истории. Спецификация
валидируется; все схемы компилируются по полному документу OpenAPI 3.1, ответы
нового модуля проверяются по нему, включая owner-редакцию и ошибки.

Настоящие migrate/admin/API и Mailpit также проверены на отдельной одноразовой
базе: полный процесс, фактическое нарушение 364 дня, исправления, права/членство,
безопасные логи, readiness и SIGTERM=0. База удалена. Седьмая миграция применена
к рабочей локальной БД: семь applied, 51 таблица с Goose, 80 FK; людей, аккаунтов,
собак, заявок и помётов нет. Readiness рабочей базы — 200, защита breeding — 401
без входа, завершение API — SIGTERM=0. Тестовые данные в рабочую базу не перенесены.

Смежные процессы: [печатные акты](documents-breeding.md), [мероприятия](events.md),
[автоматические письма](notifications.md). Отдельных карточек неидентифицированных щенков, сокращённых интервалов,
автоматического назначения медицинских нормативов и внешних интеграций нет.
