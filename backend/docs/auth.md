# Учётные записи и профили

Один человек — одна учётная запись,
несколько назначенных администратором профилей, один активный профиль в сессии.
Права профилей не складываются. Пользователь одновременно может работать как
владелец в одном браузере и как ветеринар в другом: это разные сессии одной записи.
Самостоятельной регистрации нет. Пользователь получает приглашение на email,
подтверждает владение адресом одноразовым кодом и сам задаёт пароль.

ТЗ задаёт перечень ролей;
исходная схема `club_member.role_id` сама по себе не обеспечивает модель входа
и совмещения полномочий. Источники и ограничения схемы описаны в
[database-audit.md](database-audit.md).

## Учётная запись и профиль

`users` хранит уникальные логин/email, хеш пароля, подтверждение email и статус
`invited`, `active` или `blocked`. Логин и email приводятся к нижнему регистру,
краевые пробелы удаляются. Логин: 3–64 ASCII-символа; первый — буква или цифра,
остальные — `a–z`, `0–9`, `.`, `_`, `-`. Вход выполняется по логину.

`user_profiles` связывает пользователя с ролью. Одинаковую роль одному аккаунту
дважды назначить нельзя. Профили назначает, включает и отключает администратор.

| Код | Название из справочника |
| --- | --- |
| `admin` | Администратор |
| `staff` | Сотрудник клуба |
| `veterinarian` | Ветеринар |
| `expert` | Эксперт-кинолог |
| `owner` | Владелец собаки |
| `leader` | Руководитель клуба |

Управление аккаунтами доступно только при активном профиле `admin`. Наличие
другого назначенного профиля не добавляет его прав. Самостоятельное назначение
профилей недоступно. Нельзя заблокировать или отключить последнего действующего
администратора, в том числе двумя конкурентными запросами.

Необязательный уникальный `users.club_member_id` связывает аккаунт с существующей
карточкой человека. Запись `club_member` не создаётся автоматически. Миграция
`00004_members.sql` удаляет прежнее поле `role_id`; карточки и матрица доступа реализованы в
[members.md](members.md). Неактивное членство закрывает раздел owner целиком,
включая свою карточку, но сохраняет account controls и другие включённые профили.
Статус проверяется на каждом запросе members; Profile.Enabled сам по себе недостаточен.
Администраторские права не дают ветеринарных или иных профессиональных прав.

## Токены и отзыв доступа

Access JWT действует 10 минут: HS256, проверяются подпись, `typ=at+jwt`, issuer,
audience, сроки и обязательные claims. В JWT находятся ID аккаунта, сессии,
профиля и версии; email, логин и пароль не включаются. Веб-клиент хранит access
в памяти и отправляет `Authorization: Bearer <access_token>`.

Refresh — случайный непрозрачный секрет 32 байта в cookie `dogclub_refresh`:
`HttpOnly`, `SameSite=Strict`, `Path=/api/v1/auth`, `Secure` по умолчанию.
В JSON refresh не возвращается. Локальный HTTP на loopback использует
`AUTH_COOKIE_SECURE=false`. Сессия имеет абсолютный срок 7 дней с момента входа:
обновление access не продлевает его.

При каждом защищённом запросе сервер читает PostgreSQL: аккаунт должен быть
активен, сессия — не отозвана и не просрочена, версия и профиль JWT должны
соответствовать сессии. Для административных и будущих предметных действий
дополнительно проверяются включённость и версия активного профиля. При
недоступности БД проверка возвращает 503 и не разрешает действие.
Мутации повторяют проверку полномочий внутри транзакции.

| Событие | Результат |
| --- | --- |
| Переключение профиля | Версия текущей сессии увеличивается; выдаётся новый access, прежний отвергается. Другие сессии не меняются |
| Отключение профиля | Его административные/предметные полномочия прекращаются. До истечения access доступны собственные me/profiles/switch-profile/logout/change-password |
| Повторное включение профиля | Старые полномочия JWT не восстанавливаются: требуется переключение, refresh или новый вход |
| Блокировка аккаунта | Все сессии отзываются; закрыты все профили и дальнейший вход |
| Разблокировка | Можно войти заново; прежние сессии не оживают |
| Выход | Отзывается текущая сессия; её access/refresh больше не действуют, cookie удаляется |
| Смена или восстановление пароля | Отзываются все сессии и прежние коды восстановления; требуется новый вход |

Если активный профиль отключён, refresh возвращает 403. Пока access ещё действует,
можно выбрать другой включённый профиль; после истечения access нужно заново
войти с доступным профилем. При входе можно передать `profile_id`; без него
выбирается первый включённый профиль по коду роли, затем пользователь может
переключиться.

Refresh ротируется при каждом использовании. Хранятся только SHA-256 проверочные
значения; использованные значения сохраняются для обнаружения повторной подачи.
Повтор старого refresh отзывает всю соответствующую сессию. Клиент должен
сериализовать обновления, включая разные вкладки одного браузера: параллельные
запросы с одним refresh будут расценены как повтор. Переключение профиля сохраняет
refresh-cookie, привязанную к сессии.

## HTTP и почта

Все пути ниже начинаются с `/api/v1`. Контракты тел и ответов находятся в
[OpenAPI](../api/openapi.yaml). Auth JSON ограничен 16 КиБ; неизвестные поля
отклоняются. Ошибки — RFC 9457, ответы — `Cache-Control: no-store`.

| Метод и путь | Доступ и результат |
| --- | --- |
| `POST /auth/activate` | Одноразовый код приглашения + свой пароль; 204 |
| `POST /auth/login` | Логин, пароль, необязательный profile_id; access JSON + refresh-cookie |
| `POST /auth/refresh` | Refresh-cookie; новая пара access/refresh |
| `POST /auth/forgot-password` | Логин; одинаковые 202/сообщение для доступного и неизвестного аккаунта |
| `POST /auth/reset-password` | Одноразовый код восстановления + новый пароль; 204 |
| `GET /auth/me` | Bearer; собственные аккаунт и активный профиль |
| `GET /auth/profiles` | Bearer; все свои профили, включая отключённые |
| `POST /auth/switch-profile` | Bearer + profile_id; новый access для своей включённой роли |
| `POST /auth/logout` | Bearer; отзыв текущей сессии, 204 |
| `POST /auth/change-password` | Bearer + current_password/password; отзыв всех сессий, 204 |
| `GET /users` | admin; список пользователей, limit 1–100 (50 по умолчанию), after — последний ID предыдущей страницы |
| `PATCH /users/{userID}` | admin; blocked: true/false, 204 |
| `PUT /users/{userID}/member` | admin; member_id, первоначальная привязка к карточке, 204 |
| `GET /users/{userID}/profiles` | admin; все профили аккаунта, включая отключённые; 404 для неизвестного аккаунта |
| `GET /users/{userID}/invitation` | admin; неиспользованное и неотменённое приглашение (в том числе истёкшее) без кода; 404, если его нет |
| `POST /users/{userID}/profiles` | admin; role, созданный профиль, 201 |
| `PATCH /users/{userID}/profiles/{profileID}` | admin; enabled: true/false, 204 |
| `POST /invitations` | admin; login/email/role, необязательный club_member_id; ID приглашения, 201 |
| `POST /invitations/{invitationID}/resend` | admin; новый код и ID приглашения, прежний код отзывается |
| `DELETE /invitations/{invitationID}` | admin; отмена неиспользованного приглашения, 204 |

Приглашение действует 48 часов, восстановление — 30 минут. Новый код отзывает
предыдущий код того же назначения. Повторная активация/сброс или истёкший код
дают 400 `invalid_token`. Отмена приглашения сохраняет неактивную учётную запись,
но отменённый код не даёт входа. Физическое удаление аккаунтов не реализовано.
ID профилей и действующего приглашения администратор получает повторно через
`GET /users/{userID}/profiles` и `GET /users/{userID}/invitation`: без них после
перезагрузки экрана нельзя отключить профиль, повторить или отменить приглашение.

Пароль: минимум 15 Unicode-символов, максимум 1024 байта UTF-8. Он не обрезается
и не приводится к другому регистру. Хранится Argon2id с уникальной солью:
19 МиБ, 2 прохода, параллелизм 1. Одновременно выполняются максимум два
вычисления паролей; перегрузка возвращает 429 с Retry-After.

Изменяющие браузерные запросы защищает Go CrossOriginProtection. Иностранный
Origin/Sec-Fetch-Site отклоняется с 403. CORS не включён: веб-клиент работает
с API на одном origin (сервис `web` или dev proxy Vite). CLI-запросы без Origin
могут использовать API. Cookie дополняют эту проверку атрибутом SameSite=Strict.

Ограничение попыток действует по реальному RemoteAddr и шаблону маршрута в одном
процессе, до 4096 записей. Заголовки Forwarded/X-Forwarded-For не доверенные.
Вход, активация, сброс и смена пароля — 10/мин; refresh — 60/мин;
восстановление — 5/15 мин; приглашения — 20/мин; повторная отправка — 10/мин.
Reverse proxy и распределённый лимитер не настроены.

Mailpit закреплён на `v1.31.6`, SMTP и интерфейс опубликованы только на loopback.
Внешняя доставка отсутствует. Письма содержат код для API; ссылки фронтенда пока
нет. При отказе SMTP приглашение остаётся в БД, ответ — 503 `mail_unavailable`;
заголовок Location указывает маршрут повторной отправки. При восстановлении
отказ почты не меняет публичные 202/сообщение; диагностическое событие пишется
по возможности. Одинаковое время ответа для существующего/неизвестного логина
не гарантируется: SMTP здесь синхронный.

## Первый администратор и ручная проверка

Подготовьте `.env`, запустите Compose, примените миграции и запустите API по
[README](../../README.md). Ключ JWT обязателен; в репозитории его нет.
Из второго терминала с экспортированным `.env`:

```bash
go run ./cmd/admin bootstrap admin admin@dogclub.test
```

Логин и email в команде — выбранные локальные значения, не встроенный аккаунт.
Откройте http://127.0.0.1:8025 и возьмите код из письма. Выполните запрос через
API-клиент с выбранным собственным паролем (пример JSON с placeholders):

```http
POST http://127.0.0.1:8080/api/v1/auth/activate
Content-Type: application/json

{"token":"<код из письма>","password":"<свой пароль от 15 символов>"}
```

Ожидается 204. Затем `POST /api/v1/auth/login` с `login`/`password` вернёт access
и cookie. Сохраните cookie в API-клиенте, используйте access как Bearer. Запрос
`GET /api/v1/auth/me` вернёт admin; с ним можно пригласить человека как owner,
активировать его и назначить второй профиль veterinarian.

Проверьте переключение: список `/auth/profiles`, затем `/auth/switch-profile`
с ID veterinarian. Новый access работает; старый даёт 401. У владельца запрос
`GET /users` даёт 403. После отключения veterinarian старый access ещё позволяет
переключиться обратно на owner, но не выполнять профессиональные операции.
После блокировки аккаунта прежние access и refresh дают 401 во всех сессиях.

Bootstrap работает только до появления первого admin-профиля. При сбое SMTP
можно повторить ту же команду с теми же login/email для ещё не активированного
первого администратора; старый код при этом отзывается. После активации новые
администраторы приглашаются обычным admin API. Автоматического восстановления
доступа через bootstrap при блокировках нет.

## Хранение и проверки

Миграция `00003_auth.sql` добавляет users, user_profiles, auth_invitations,
auth_sessions, auth_refresh_tokens, auth_password_resets, auth_events и role.code.
Первые две миграции не изменены. Auth-связи используют RESTRICT; составной FK
сессии исключает профиль другого аккаунта. Изменения сериализуются короткой
транзакционной advisory lock PostgreSQL; SMTP и Argon2 находятся за её пределами.
Это обеспечивает атомарность ротации и защиты последнего администратора.

События содержат тип, время, ID исполнителя/цели и request_id; паролей, исходных
токенов и текстов писем в них нет. Отсутствуют автоматическая очистка журнала,
истёкших сессий и использованных проверочных значений, UI управления и внешний
SMTP. Политика хранения требует отдельного решения перед эксплуатацией.

```bash
gofmt -l cmd internal migrations api
go vet -tags=integration ./...
go test -race -count=1 ./...
export DOGCLUB_TEST_DATABASE_URL="$DATABASE_URL"
go test -race -count=1 -tags=integration ./...
go build -o bin/ ./cmd/...
go mod verify
docker compose config --quiet
git diff --check
```

Интеграционные тесты создают случайные одноразовые БД и удаляют только их;
рабочая БД из URL не мигрируется тестами. Нужны права CREATEDB. SMTP в тестах
сервиса заменяется записывающим адаптером; реальная доставка дополнительно
проверена на Mailpit с настоящими CLI/API и отдельной одноразовой БД.
Готовые пользователи и пароли в рабочую БД не добавлялись.
